# 0003 Login per Passwort und OIDC
Status: angenommen (2026-10-08, Interview Runde 3)
Kontext: Single-User; Eduard nutzt primär seinen OIDC-Provider, Passwort als Fallback.
Entscheidung: Beide Methoden ab v1. Passwort als argon2id-Hash per Env/Secret; OIDC Authorization Code + PKCE (go-oidc), Allowlist für `sub` oder verifizierte E-Mail; serverseitige Sitzungen in SQLite, Cookie `__Host-…`, CSRF über `http.CrossOriginProtection` + SameSite=Lax.
Konsequenzen: Keine Benutzerverwaltung/kein Passwortwechsel in der UI; Start schlägt fehl ohne konfigurierte Methode bzw. ohne OIDC-Allowlist. Details: SPEC.md §9.
Nachtrag 2026-10-18 (Issue #47): Der **Ablageort** des Passworts ist revidiert — der Hash liegt jetzt als Zeile `password_hash` in `system` (`belegapp set-password`, Wechsel in `Einstellungen → Passwort`), nicht mehr in einem Secret. Zusätzlich kommt eine **dritte Methode** dazu: vertrauenswürdige Header. `BELEGAPP_AUTH_HEADER_ENABLED=true` nimmt den Wert von `BELEGAPP_AUTH_HEADER_NAME` als Identität an, aber nur aus `BELEGAPP_TRUSTED_PROXIES` und nur für Werte in `BELEGAPP_AUTH_HEADER_ALLOWED`; beide Pflichtangaben sind Startfehler. Damit braucht eine Instanz hinter Forward-Auth weder Passwort noch OIDC, und der Betreiber meldet sich nicht ein zweites Mal an. Unverändert bleiben OIDC (PKCE, Allowlist), die serverseitigen Sitzungen, Cookie und CSRF. Details: SPEC.md §9.1/§9.2/§9.6.
